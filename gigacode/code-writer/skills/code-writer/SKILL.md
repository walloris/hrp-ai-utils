# Skill: code-writer

Реализует задачу в коде, опираясь на память проекта и существующие паттерны модуля.

## Запрещено

- Не придумывай требования, которых нет в задаче.
- Не пропускай чтение памяти проекта, если `.gigacode/memory/` существует.
- Не дублируй правила проекта из памяти в ответе и не заменяй их своими общими предпочтениями.
- Не делай лишний рефакторинг вне задачи.
- Не меняй несвязанный код "заодно".
- Не создавай новые абстракции, интерфейсы, конфиги и слои без явной необходимости.
- Не считай задачу завершённой без проверки результата.

## Порядок работы

Следуй шагам по порядку.

### Шаг 1. Разобрать задачу

Если в запросе указан номер Jira-задачи — получи описание задачи через интеграцию Jira.

Зафиксируй:
- что нужно сделать;
- ожидаемый результат;
- входные данные;
- ограничения;
- неясности и допущения.

Если требования неполные:
- явно перечисли неопределённости;
- не заполняй пробелы выдуманными решениями;
- опирайся только на текст задачи и код проекта.

### Шаг 2. Прочитать память проекта

Если существует `.gigacode/memory/`:

Прочитай обязательно:
- `.gigacode/memory/conventions.md` — соглашения и триггеры для references

Прочитай при необходимости:
- `.gigacode/memory/project.md` — если нужны команды запуска, точки входа, структура директорий
- `.gigacode/memory/architecture.md` — если задача затрагивает интеграции, потоки данных, компоненты
- `.gigacode/memory/stack.md` — если нужно уточнить зависимости или инфраструктуру

После этого определи, нужны ли дополнительные reference-файлы.

Читай `references/*` только если задача затрагивает соответствующий аспект:
- `references/naming.md` — когда создаёшь или переименовываешь сущности;
- `references/layering.md` — когда выбираешь слой, пакет, модуль или wiring;
- `references/error-handling.md` — когда меняешь обработку ошибок;
- `references/testing.md` — когда добавляешь или правишь тесты;
- `references/api-patterns.md` — когда меняешь endpoint, DTO, request/response, контракты.

Если задача затрагивает несколько аспектов — читай все релевантные reference-файлы, но не открывай нерелевантные.

Если `.gigacode/memory/` отсутствует:
- работай только по подтверждённым фактам из кода;
- перед изменениями изучи существующие паттерны в затронутом модуле.

### Шаг 3. Изучить релевантный код

Изучи только ту часть проекта, которая относится к задаче.

Найди и зафиксируй:
- затронутый модуль;
- точку входа или вызывающий код;
- похожую реализацию;
- связанные модели, сервисы, репозитории, API или хендлеры;
- существующие тесты;
- локальные паттерны именно этого модуля, если они отличаются от общепроектных.

Приоритет стиля:
1. локальный стиль модуля;
2. общие правила из `conventions.md`;
3. общие паттерны проекта, подтверждённые кодом.

Перед изменениями кратко зафиксируй:
- где будет сделано изменение;
- что будет переиспользовано;
- что создавать не нужно;
- критерий успешности.

### Шаг 4. Реализовать минимальное решение

Пиши минимально необходимый код для выполнения задачи.

Правила выполнения:
- меняй только то, что относится к задаче;
- переиспользуй существующие сущности, если они подходят по смыслу;
- новый код размещай в том слое и модуле, где ему логически место;
- следуй naming, layering, API и testing conventions из памяти проекта;
- если локальный модуль живёт по своим правилам — следуй локальному стилю модуля;
- не добавляй комментарии без необходимости;
- не вноси декоративные правки.

Если по ходу реализации появляется архитектурная развилка:
- явно сформулируй варианты;
- выбери только тот, который минимален и лучше согласуется с текущим кодом;
- если выбор нельзя подтвердить кодом или задачей, зафиксируй неопределённость.

### Шаг 5. Проверить результат

Запусти только релевантные проверки, которые реально относятся к задаче:
- компиляция или сборка затронутого модуля;
- тесты затронутого модуля или сценария;
- форматирование или линтер, если это принято в проекте;
- дополнительные проверки из project memory, если они явно указаны.

Не запускай бессмысленно весь набор команд, если достаточно локальной проверки.

Если проверка упала:
- исправь причину;
- повтори проверку;
- не завершай работу с красным состоянием без явной фиксации проблемы.

## Формат результата

В финале дай короткий отчёт:

### Что сделано
- список изменений по сути задачи

### Где изменено
- файлы и модули

### Что проверено
- какие проверки запускались
- что прошло
- что не удалось проверить

### Неопределённости
_Указывай только если есть. Если всё ясно — раздел не включай._

## Coding rules

- Think Before Coding:
  - явно проговаривай допущения;
  - не принимай скрытых решений за пользователя;
  - если что-то неясно, фиксируй неопределённость.

- Simplicity First:
  - пиши минимально необходимый код;
  - не добавляй абстракции, интерфейсы, конфиги и слои "на будущее";
  - не усложняй решение без необходимости.

- Surgical Changes:
  - меняй только то, что нужно для задачи;
  - не рефактори соседний код "заодно";
  - не форматируй и не переписывай несвязанные части файла;
  - не удаляй код вне задачи.

- Goal-Driven Execution:
  - перед изменениями формулируй критерий успеха;
  - работай маленькими шагами;
  - проверяй результат по тесту, сценарию или ожидаемому поведению.
