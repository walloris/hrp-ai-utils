# Command: memory:update

Режим: **update** — `.gigacode/memory/` существует, контекст устарел.

Обновляет существующую память проекта без пересоздания с нуля.

---

## Шаг 0 — Чтение текущей памяти

Перед анализом прочитай актуальное состояние:
- `.gigacode/memory/project.md`
- `.gigacode/memory/architecture.md`
- `.gigacode/memory/stack.md`
- `.gigacode/memory/conventions.md`

Зафиксируй, что уже известно. Это база — не перезаписывай без причины.

---

## Шаг 1 — Дельта-анализ проекта

Исследуй проект с акцентом на изменения:

1. Прочитай `README*`, `docs/` и корневые markdown-файлы
2. Изучи структуру директорий на глубину 2–3 уровня
3. Найди build/config файлы:
   - `build.gradle.kts`, `build.gradle`, `settings.gradle`, `pom.xml`
   - `pyproject.toml`, `requirements.txt`, `poetry.lock`
   - `package.json`, lockfiles
   - `Cargo.toml`, `go.mod`
   - `Makefile`, `Taskfile.yml`
   - `docker-compose.yml`, `compose.yml`, `Dockerfile`
   - `.env.example`, `.env.sample`
4. Сравни с тем, что было в памяти:
   - появились новые модули / сервисы / entrypoints?
   - изменился стек (новые зависимости, убрали старые)?
   - изменились команды запуска или тестов?
   - появились новые интеграции?
   - изменились соглашения?

Если изменений нет — зафиксируй это явно и не перезаписывай файлы.

---

## Шаг 2 — Полнота покрытия

Проведи 2 прохода по конечным наборам сущностей.

### Проход 1
Найди актуальные конечные наборы:
- модули
- сервисы
- пайплайны
- команды CLI
- интеграции
- entrypoints
- конфигурационные профили

Для каждого набора:
1. Найди источник истины: enum, sealed class, config, registry, factory
2. Составь полный актуальный список
3. Зафиксируй количество

### Проход 2
Сравни актуальный список с тем, что записано в памяти.
Если найдено больше сущностей — дополни память.
Не завершай update, пока покрытие не полное.

Фиксируй покрытие явно:
- `Template types: n из n`
- `Entrypoints: n из n`
- `Main modules: n из n`

---

## Шаг 3 — Обновление соглашений

Проверь, не изменились ли паттерны. Найди до 3 representative files для изменившихся слоёв:
- controller / api
- service / usecase / handler
- repository / dao / gateway
- config / infrastructure
- dto / model / schema
- tests

Обновляй `references/*.md` только если паттерн действительно изменился.
Не трогай файлы, которые остались прежними.

Confidence:
- 1 пример → `low`
- 2–3 совпадающих примера → `medium`
- устойчивый паттерн → `high`

---

## Шаг 4 — Обновление файлов памяти

Обнови только те файлы, в которых есть реальные изменения:

```text
.gigacode/memory/
├── project.md        ← обновить дату, entrypoints, команды, модули
├── architecture.md   ← обновить компоненты, интеграции, покрытие
├── stack.md          ← обновить зависимости, инструменты
├── conventions.md    ← обновить только изменившиеся соглашения
└── references/       ← обновить только изменившиеся файлы
```

В каждом обновлённом файле: обнови дату последнего обновления памяти.

---

## Шаг 5 — Завершение и валидация

1. Проверь:
   - все memory-файлы существуют
   - неизвестные данные помечены `<не определено>`
   - покрытие сущностей полное
   - `conventions.md` основан на реальных примерах
   - для conventions выставлен confidence
   - в `project.md` нет раздела про references
   - в `conventions.md` нет дублирующего раздела `## References`

2. Ответь пользователю:

```text
✅ Онбординг завершён

Режим: update

Обновлено:
- .gigacode/memory/project.md
- <другие изменённые файлы>

Без изменений:
- <неизменённые файлы>

Проект: <название>
Стек: <основные технологии>
Покрытие:
- Entrypoints: <n из n>
- Main modules: <n из n>
- Key finite sets: <n из n>
```

---

## Жёсткие правила

- не придумывай информацию
- подтверждай факты только файлами проекта
- если факт не найден, используй `<не определено>`
- не меняй пользовательский код
- не перезаписывай файлы без реальных изменений
- не считай анализ завершённым без проверки полноты покрытия
- не считай conventions установленными без реальных примеров
